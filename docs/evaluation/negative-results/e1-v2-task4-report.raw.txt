## Round-3 immutability hardening

- `CandidateSelectionRecord` exposes neither audit status as a constructor/dataclass
  field. Both are read-only `UNVERIFIED` properties, so ordinary construction,
  `dataclasses.replace`, and direct slot assignment cannot forge `VERIFIED`.
- Construction recursively copies and freezes every retained audit-evidence mapping and
  array as ordered mapping proxies and tuples. Source dictionaries/lists, nested retained
  data, and independent records share no mutable aliases. Non-string mapping keys,
  nonfinite numbers, sets, and other non-JSON values are rejected.
- Every `as_record()` call recursively thaws into a fresh JSON-compatible dictionary/list
  tree. Mutating one export cannot alter the selection, evidence, self-hash, ranking,
  outcome, or any later export.
- `verify_candidate_selection_audit()` is procedural: it runs the complete exact audit,
  raises on any failure, returns `None` on success, and retains no verification status.
  Callers needing selection semantics use the pure loader separately and receive only an
  immutable `UNVERIFIED` record.
- No `VerifiedCandidateSelectionAudit`, capability token, minting function, or runtime
  `VERIFIED` symbol/state exists. This avoids making an unprovable durable in-process trust
  claim under Python reflection and leaves the reviewer attacks with no target.
- The checked schema and selection semantics did not change. The checked record was
  repaired only to bind the changed diagnostics source projection, using the immutable
  original candidate artifacts and stored transforms without comparison, search,
  candidate inference, or benchmark reruns.
